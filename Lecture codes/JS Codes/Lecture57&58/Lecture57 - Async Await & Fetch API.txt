Most of the latest softwares make heavy use of async await and fetch API, because these techniques help us write clean and fast code along with making the code easy to debug.

The main motive of Async Await code is to depict the async code as a sync code. In simpler words, using async await, we can execute an async code as a sync code (give async code sync behaviour). 

Example:

// Sync code block

// Async code block

// Sync Code block

If we want the async code block to execute after the first sync code block, then we will have to use the await function, then what will happen is when the parser reaches sync code, it will execute it and show the output, then move to the async code block and fully execute it, that means the parser will wait the entire async code is execute and once we receive a promise fulfilled or rejected message, then only it will move forward to the second sync code block.

When we had the concept of promises, the concept of Async await was introduced to write clean code which is easier to debug and properly manage the concept of promises. Async await is a special syntax using which we can efficiently write and handle promises.

Async function will always return a promise. IMPORTANT
To verify that an async function always returns a promise:

async function getData() {
    setTimeout(function() {
        console.log("I am inside getData, setTimeout function")
    }, 3000);
}

let output = getData();         // We see in browser console that we have received a promise in return.

FETCH API: Fetch API provides an interface for fetching resources (including across the internet), it is more powerful and flexible than XMLHttpRequest.

Now we will execute a normal get request using fetch API: (we will request on a website developed for this task: https://jsonplaceholder.typicode.com/)

Whenever we write a fetch request, then we have the following flow:
1. Prepare URL / API Endpoint which we want to fetch the data from -> This is sync in nature because we know the endpoint and we will fetch the data present there.
2. Fetch data from the endpoint -> This might involve a lot of network calls / complex function on the endpoint while fetching, therefore this is Async in nature.
3. Process the received data -> Sync in nature, processes like printing or returning the data are sync in nature.

This is why we needed async await function because if the network call or the complex functions in the 2nd step take time and the execution flow moves to the next step that is processing the data, but the main thing is we have not received any data from the endpoint so on which data are we going to run the processes on (it will simply return undefined as the data has not been received yet)? That was the problem.
Async Await lets us put a condition on the code that unless we have not received data from the second step, we will not move forward to the next step.

Code Example:
async function getData() {

    // Get request -> Async in nature
    let response = await fetch('https://jsonplaceholder.typicode.com/posts');

    // Pasring recevied JSON -> Async in nature
    let data = await response.json()

    console.log(data); 
}        // Always remember that the await keyword can only be applied inside of async function

getData();

We have marked both the fetch request and response.json() as await because they both are async in nature and we dont want to print data unless we have populated everything inside the data variable.

WHY IS response.json() async?
When fetch completes, it gives you a Response object — but this response object only contains the headers of the response at that point. The actual body data (the JSON) is still being streamed/transferred.
Think of it like this:
- fetch is like ordering food → you get a token (response object) saying your order is placed
- response.json() is like actually receiving and unpacking the food → takes more time


The above code is only for the GET request, for other types of request like PUT / DELETE or POST, we will have to pass more parameters as input, they are called Options.

// ============================================================
// HTTP HEADERS - Complete Explanation
// ============================================================

// Headers are KEY-VALUE pairs sent along with every
// HTTP request and response
// Think of them as METADATA - extra information about the request
// Like a cover letter that comes with your actual data

// ============================================================
// ANALOGY
// ============================================================

// Imagine you're sending a package (your request):
// - The PACKAGE is your actual data (body)
// - The LABEL on the package is the HEADER
//   → what's inside (Content-Type)
//   → who it's from (Authorization)
//   → what language (Accept-Language)
//   → how big is it (Content-Length)


// ============================================================
// TWO TYPES OF HEADERS
// ============================================================

// 1. REQUEST HEADERS  → sent by YOUR browser/code to the server
// 2. RESPONSE HEADERS → sent by the SERVER back to you


// ============================================================
// MOST COMMON HEADERS YOU'LL USE
// ============================================================

// 1. Content-Type
//    → tells the server what FORMAT your data is in
myHeaders.append("Content-Type", "application/json");  // sending JSON
myHeaders.append("Content-Type", "text/html");         // sending HTML
myHeaders.append("Content-Type", "multipart/form-data"); // sending a form

// 2. Authorization
//    → proves who you are to the server (like a password)
myHeaders.append("Authorization", "Bearer your_token_here");
//    → most APIs require this to verify you have access

// 3. Accept
//    → tells server what FORMAT you want the response in
myHeaders.append("Accept", "application/json"); // i want JSON back
myHeaders.append("Accept", "text/html");        // i want HTML back

// 4. Content-Length
//    → automatically set, tells server how big your data is
//    → you rarely set this manually


// ============================================================
// HOW TO CREATE AND USE HEADERS IN FETCH
// ============================================================

// METHOD 1 - Using Headers object (cleanest way)
const myHeaders = new Headers();
myHeaders.append("Content-Type", "application/json");
myHeaders.append("Authorization", "Bearer mytoken123");

// METHOD 2 - Plain object (shortcut, works the same)
const response = await fetch("https://api.example.com/data", {
    method: "GET",
    headers: {
        "Content-Type": "application/json",   // ← same thing
        "Authorization": "Bearer mytoken123"  // ← just simpler syntax
    }
});


// ============================================================
// REQUEST vs RESPONSE HEADERS EXAMPLE
// ============================================================

// YOUR REQUEST HEADERS (you send these):
// Content-Type: application/json   → "i am sending JSON"
// Authorization: Bearer xyz        → "here is my token"
// Accept: application/json         → "send me JSON back"

// SERVER RESPONSE HEADERS (server sends these back):
// Content-Type: application/json   → "i am sending JSON back"
// Content-Length: 1024             → "my response is 1024 bytes"
// Status: 200 OK                   → "everything went fine"

// You can READ response headers like this:
const response = await fetch("https://api.example.com");
console.log(response.headers.get("Content-Type")); 
// → "application/json"


// ============================================================
// HTTP STATUS CODES (come in response headers)
// ============================================================

// 200 → OK, everything worked
// 201 → Created, new resource was made
// 400 → Bad Request, you sent wrong data
// 401 → Unauthorized, you need to login
// 403 → Forbidden, you don't have permission
// 404 → Not Found, resource doesn't exist
// 500 → Internal Server Error, server side problem


// ============================================================
// ONE LINE SUMMARY
// ============================================================

// Headers are metadata attached to every HTTP request/response
// They tell both sides HOW to handle the data being sent
// like Content-Type tells "what format", 
// Authorization tells "who you are"
// Accept tells "what you want back"
